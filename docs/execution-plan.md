## 1. 최종 목적과 범위

**많은 실제 작품을 작가별로 축적하고, 출처와 변경 이력을 보존하면서 참고사이트·블로그로 감상과 조사를 이어가는 아카이브를 만든다.**

첫 공개는 **모바일·PC를 지원하는 반응형 웹**으로 진행한다. 모바일은 감상·저장·읽기, PC는 다수 작품 탐색과 운영에 집중하되 핵심 기능과 계정·데이터를 공유한다. PWA와 iOS·Android 전용 앱은 이번 공개 구현·공수에 포함하지 않는다. 공개 후 반복 이용과 실제 요구에 따라 필요성을 평가하며, 플랫폼 판단 기준은 상위 기획안 15절을 따른다.

DailyArt에서는 한 작품에서 감상을 시작하는 방식을, 29Magazine에서는 주제·연재로 읽을거리를 묶는 방식을 참고한다. 기반은 작품·작가 데이터이며, 홈의 추천과 글은 그 자료를 소개한다. 세 영역의 콘텐츠를 복제하지 않고 관계로 연결한다. 관찰 근거와 확인 범위는 [레퍼런스 조사](../research/art-collection/reference-sites.md)에 남겨 두었다.

| 단계 | 계획 수량 | 통과 목적 |
| --- | --- | --- |
| 현재 표본 | 실제 작품 30점, 확인된 작가 19명, 미상 작품 4점 | 자료 구조와 작가 연결 검토용; 첫 공개 분량 아님 |
| 시험 수집 | 중복 제거한 작품 1,000점 | 처리 시간·검토량·품질·비용·복원 가능성 측정 |
| 첫 공개 | 이미지와 기본 정보가 검증된 약 5,000점, 확인된 작가 100명 이상 | 작가별 탐색이 가능한 대규모 아카이브 |
| 첫 공개 편집물 | 참고사이트 8건, 블로그 4편, 공개 컬렉션 2개 | 세 영역을 연결하는 실제 이용 흐름 |
| 지속 확장 | 10,000점 이상 | 신규 작가와 기관 추가, 기존 작가의 수집 깊이 보완 |

수량은 기획상 목표다. 1,000점 시험 결과에서 원자료의 범위와 비용을 확인해 조정하며, 변경 이유와 새 목표를 기록한다. 우선 작가 20명은 작가당 20점 이상 확보 가능한지 조사한다. 확보가 어려운 작가는 확인된 범위와 이유를 공개한다. 숫자를 맞추기 위한 중복 등록이나 미상 작가의 인위적인 분할은 허용하지 않는다.

## 3. 구현 기준과 데이터 계약

### 3.1 재사용 범위

| 코드에서 확인한 지점 | 실행 결정 |

| 갤러리 개별 업로드 화면 | 기존 8MB 제한·디자인 분류와 독립된 대량 작품 수집 경로 구축 |

이는 코드 관찰을 바탕으로 한 구현 판단이다. 기존 서비스가 잘못 동작하거나 권한에 문제가 있다는 진단은 아니다. UI 전면 재작성이나 프레임워크 교체를 선행 조건으로 두지 않는다.

### 3.2 최소 데이터 관계

아래 이름은 논리적 데이터 단위다. 실제 테이블명·마이그레이션은 기존 DB 조사 후 정한다.

| 데이터 단위 | 필수 계약 |
| --- | --- |
| 작품 | 영구 내부 ID, 원문 제목, 한글 제목과 번역 검토 상태, 날짜 원문과 확인 가능한 범위, 재료·크기·기관, 검증·공개 상태 |

| 작품–제작자 관계 | 여러 제작자 허용; 제작·공방·귀속 추정 등 원문 역할과 확실성 보존; 미상은 작품 상태 |

| 이미지 자산 | 연결 작품·출처, 파일 위치·MIME·크기·해상도·체크섬, 원본/파생본 구분, 이용 근거와 확인일, 공개 가능 상태 |
| 수집 실행 | 대상·진행 위치·성공/실패/보류 수·재시도·시작/종료·오류 사유; 재실행 가능한 범위 |
| 변경 이력 | 변경 전후·주체·이유·시간; 작가/작품 병합과 분리 시 이전 ID의 처리 기록 |
| 편집·연결 | 해설과 블로그 발행 상태, 작품·작가·사이트 연결, 공개 컬렉션 항목 순서 |

출처 레코드 수·고유 작품 수·이미지 파일 수는 서로 다르게 집계한다. 같은 제목이나 같은 파일 해시만으로 작품을 합치지 않는다. 판본·다폭 작품·상세 촬영은 원자료의 소장품 단위와 관계를 보존하고 의심 사례를 검토 대기열로 보낸다. 작가 미상은 작가 수에 포함하지 않는다.

### 3.3 공개·권한·파일 보존

자료 검증, 공개 여부, 해설 완성도를 분리한다. 공개 목록·검색·작가 수량·관련 자료에는 공개 상태를 일관되게 적용하고, 비공개 전환 시 해당 캐시도 갱신한다. 이미지 이용 근거가 바뀌면 이미지 제공을 중단하고 근거 및 조치 이력을 남긴다. 자료 레코드의 공개 가능성은 별도로 확인한다.

API에 노출하는 테이블은 grants와 RLS를 각각 설계·검증한다. 개인 저장은 본인 행만 접근하게 하고, 수집 권한은 서버 작업에 한정한다. 원자료·검토 중 파일·백업은 공개 영역과 분리한다. 공개 버킷의 파일은 DB 공개 상태만 바꾼다고 접근이 차단되는 것으로 간주하지 않으며, 파일 제공 중단과 CDN 캐시 처리도 검증한다. 근거: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

운영 계정·요금제·현재 정책은 미확인이다. 구현 착수 시 설치 버전과 실제 프로젝트 설정을 확인하고 [공식 변경 이력](https://supabase.com/changelog)과 대조한다. 요금제의 자동 백업만으로 이미지 파일 복원이 해결된다고 가정하지 않는다.

## 5. 단계별 품질과 성능 기준

### 시험 수집 통과: C02

- 공개 후보 전수 자동 검사: ID·출처·제작자 관계 또는 미상 상태·이용 근거·이미지 디코딩·원본 해시·파일 존재·유효 연결 확인. 원출처에 없는 연대·재료 등은 누락 사유를 보존하며 임의로 채우지 않는다.
- 수동 표본: 1,000점 중 최소 100점. 기관·주요 작가·미상·유형별로 층화하고 드문 제작자 관계와 귀속 추정 사례를 포함한다. 자동 검사에서 발생한 예외는 표본과 별도로 전부 해결하거나 비공개 대기한다.
- 원본과 화면 이미지의 작품 일치, 제작자 매핑, 번역 상태를 대조한다. 중대한 오류가 한 건이라도 나오면 같은 변환 규칙·기관·유형의 영향 범위를 확대 조사하고 수정 후 다시 검사한다.
- 재실행·중단 재개·원출처 변경·중복 의심·작가 병합과 분리·이미지 제공 중단 시나리오를 통과한다. 사람의 표본 검토만으로 전수 정확도를 보장했다고 표현하지 않는다.

### 공개 규모 통과: F02·F03

- 5,000점 후보 전수 자동 검사와 최소 5%인 250점 수동 층화 검토를 수행한다. 1,000점 이후 새로 들어온 기관·작가·유형을 포함하고, 규칙 변경 영향을 받은 이전 자료도 재검증한다.
- 이미지·출처 불일치, 타인의 저장 정보 접근, 비공개 노출, 자료 유실, 핵심 이용 흐름 실패는 해결 전 공개하지 않는다. 부가 해설 누락은 공개를 막지 않는다.
- 검색 결과와 작가 수량은 동일한 공개 조건을 기준으로 산출한다. 제작 연도가 불명확한 작품은 미상으로 필터링하고, 연대순 정렬에서 처리 위치를 명시한다. 정렬 기준이 같으면 영구 ID로 순서를 고정한다.
- 목록은 기본 24점, 최대 48점의 UI 페이지로 제공한다. 페이지 변경·검색어·필터·정렬을 주소에 반영하고 조건 변경 시 첫 페이지로 이동한다. 이미지 전체를 한 번에 내려받지 않는다.
- 성능 목표 제안: 실제 5,000점 데이터, 검증 환경에서 동시 사용자 10명, 10분간 혼합 목록/검색/작가 상세 요청의 응답시간 p95 2초 이하. 캐시가 있는 경우와 없는 경우를 구분해 기록하고, 준비 실행은 집계에서 제외한다. 기관 API 호출은 사용자 검색 경로에 포함하지 않는다.
- Chrome의 고정 모바일 네트워크 설정과 실제 모바일에서 첫 작품 노출·이미지 확대·뒤로 가기·로그인 후 복귀를 확인한다. iOS Safari·Android Chrome·PC Chrome/Edge를 초기 검증 대상으로 삼고 테스트 버전과 기기를 기록한다. 핵심 기능이 화면 크기에 따라 사라지지 않는지, 필터·본문·작품 비율·터치 조작·가로 넘침을 확인한다. 접근성은 키보드 이동, 포커스 표시/복귀, 이미지 대체 설명, 확대 화면 닫기를 검수한다.
- 기존 사이트의 build·lint 실행 결과를 기록하고 기존 결함과 새 결함을 구분한다. 의미 있는 자동 검증은 수집 재개·중복·권한·집계에 집중하며 문서나 단순 화면 문구를 위한 테스트를 늘리지 않는다.

성능 숫자는 현재 측정 결과가 아닌 합격 목표다. C03에서 실제 인프라를 기준으로 수정할 수 있지만, F02 결과를 보고 불리한 수치만 제외하지 않는다.

## 6. 실제 콘텐츠 제작 계획

### 수집처와 작가

초기 자동 수집은 표본을 확보한 Met·Cleveland부터 구현한다. 공개 정책은 기관 안내와 개별 레코드의 상태를 함께 확인한다. NGA는 다음 수집처 후보이며 API·일괄 자료·이미지 연결을 별도 검증한다. e뮤지엄은 우선 한국어 정보와 소장처 조사에 활용하고 대량 이미지 수집 가능성을 전제하지 않는다. DailyArt·29Magazine은 경험과 편집의 레퍼런스이며 해당 서비스의 글·이미지를 통째로 옮기는 소스로 사용하지 않는다.

우선 작가 목록은 유명도만으로 정하지 않는다. 현재 19명의 표본을 출발점으로 작품 확보 가능량, 여러 기관의 자료, 지역·시기·매체 다양성을 비교해 A04에서 20명을 선정한다. 특정 문화권 자료가 부족하면 실제 부족 범위를 기록하고 다음 수집 우선순위에 반영한다.

## 7. 공개·복구·운영 절차

### 공개 조건

G01에서 작품·이미지·작가의 실제 공개 수, 우선 작가 수집 범위, 8개 사이트·4편 글·2개 컬렉션, F02~F04 증거를 하나의 판정서에 기록한다. 5,000점/100명 목표가 조정되면 원자료 제약·품질·비용에 따른 이유와 새 수량을 명시한다. 핵심 데이터 정확성·권한·복원 조건은 수량 조정으로 대체하지 않는다.

### 배포 순서

1. 공개 대상 데이터와 코드 버전을 고정하고 배포 직전 DB·원자료·파일 목록의 복구 지점을 확보한다.
2. 검증 환경에서 확인한 추가형 스키마를 적용한다. 기존 데이터 제거는 이번 공개 배포와 분리한다.
3. 운영 코드를 배포하고 공개 플래그를 적용한다. 관리자 확인 중 자료가 미리 노출되지 않게 한다.
4. 실제 주소에서 익명 감상, 작가 검색, 필터·뒤로 가기, 원사이트 이동, 본인 저장, 타인 접근 차단을 확인한다.
5. 오류·이미지 실패·응답시간·비공개 노출을 점검하고 실행 버전과 결과를 기록한다.

### 실패 시 복구

자료 훼손이나 권한 문제가 발견되면 영향받은 자료 제공·수집을 즉시 중단한다. 코드 문제는 이전 검증 버전으로 되돌리고, 새 스키마는 기존 버전과 호환되는 범위에서 보존한다. 배포 후 생긴 저장·편집 기록을 지우는 일괄 DB 복원을 기본 조치로 사용하지 않는다. 데이터 문제는 수집 실행 ID·변경 이력으로 영향을 특정하고 수정 또는 선택 복원한다. 전체 복원이 필요하면 새 변경분 보존 방법과 영향 범위를 먼저 확정한다.

이미지 제공 중단은 DB 상태, 공개 파일 접근, 파생본, CDN 캐시를 함께 처리한다. 잘못 병합한 작가/작품은 이전 관계를 복원하고 영구 주소 연결을 확인한다. 백업은 실제 복원 결과와 해시 검증까지 기록해야 성공으로 간주한다.

### 운영 일정 기준

| 주기 | 담당과 작업 | 남길 기록 |
| --- | --- | --- |
| 매일 | 운영: 수집 실패·보류·이미지 오류·백업 결과 점검 | 실행 수량, 실패 원인, 조치 대상 |
| 매주 | 편집: 작가별 부족 자료·번역·새 글 편성; 운영: 파일 무결성 순환 점검 | 작가별 증가량, 예외 잔량, 편집 실적, 검사 범위 |
| 매월 | 운영: 격리 환경 표본 복원; 편집: 사이트 링크·정보 재확인 | 복원 시간·누락·해시 결과, 링크 변경과 확인일 |
| 신규 기관·큰 구조 변경 시 | 개발·운영: 해당 범위 수집/권한/복원 재검증 | 변경 전후 검증 보고 |

메타데이터는 일별 백업, 원본·원자료는 수집 배치 종료 시 독립 백업에 반영하는 것을 초기 기준으로 한다. 백업 보관 기간·접근권한·실행 시각·허용 데이터 손실/복구 시간은 A01과 C03에서 실제 예산에 맞춰 정한다. 주간 파일 검사는 순환 범위를 기록하고 월내 전체 원본을 확인하는 것을 목표로 한다. 정기 실행은 구현·검증 후 설정하는 작업이며 현재 자동화가 생성된 것은 아니다.

공개 후 1~7일은 오류와 검색 실패 보완, 8~14일은 탐색·저장 지표의 기준선 확보, 15~30일은 비교와 운영량 조정에 집중한다. 10,000점 확대는 30일 안에 반드시 끝내는 일정이 아니라 G03에서 품질·비용·운영 여력을 확인한 뒤 실행하는 후속 목표다.

G03에는 모바일·PC별 재방문과 저장 자료 재열람, 설치·위젯·오프라인 요청을 포함한다. 표본이 부족하면 플랫폼 결정을 유보하고 관찰을 계속한다. G05는 앱 제작 약속이 아닌 평가 작업이다. PWA가 선택되면 설치·재실행·업데이트·캐시·로그아웃 처리를 검증하고, 전용 앱이 선택되면 공통 계정·자료 연결과 핵심 추가 기능의 시제품을 별도 범위로 산정한다. 작품 수 확대 G04와 플랫폼 선택 G05는 독립적으로 판단한다.

## 8. 일정·비용·위험 관리

### 공수 가정

아래는 실제 1,000점 측정 전의 초기 계획 추정이다. 개발자 1명 기준 작업일이며, 자료 조사·원고·검수의 편집 공수와 외부 응답 대기는 별도다. 일정 약속이나 견적이 아니다.

이 공수는 모바일·PC 반응형 웹과 웹 관리 화면의 첫 공개 기준이다. 설치형 웹, 전용 앱, 앱스토어 배포, 위젯·알림·오프라인 감상 개발은 포함하지 않는다. G05 평가 후 선택한 범위는 별도 산정한다.

| 구간 | 개발·운영 작업일 가정 | 주요 변동 요인 |
| --- | --- | --- |
| A 현황·설계 | 3~5일 | 기존 DB·배포·역할 정책 파악 |
| B 수집·보존 기반 | 10~15일 | 원자료 차이, 재개·변경·작가 병합 처리 |
| C 1,000점 시험 | 3~5일 | 기관 응답과 실패율, 예외 검토 |
| D 아트·작가 화면 | 8~12일 | 검색·집계·이미지·관리 화면 |
| E 기존 기능 연결 | 5~8일 | 기존 저장·편집 구조와 호환 |
| F 규모 확대·검수 | 6~10일 | 5,000점 품질·성능·전체 복원 |
| G01~G02 공개·인수 준비 | 2~3일 | 배포 환경과 장애 대응 |
| 합계 | 37~58일 | 개발자 1명, 주 5일이면 약 8~12주 + 외부 대기 |

편집·자료 조사·수동 검수는 별도 12~20인일을 초기 가정으로 잡고 C02에서 실측한다. 같은 사람이 개발과 편집을 모두 수행하면 두 공수를 더해 약 49~78작업일을 예상하며 동시 진행으로 계산하지 않는다. 공개 후 30일 운영 관찰은 위 제작 기간 이후다. 외부 원자료나 예외량 때문에 기간이 늘어나면 부가 해설·후속 기능을 줄이고 출처·작가 정리·복원 검증은 유지한다.

### 저장·전송 비용 산정

현재 표본 원본 30개의 합은 103,475,299바이트로 평균 약 3.45MB다. 단순 외삽하면 원본만 5,000점 약 17.2GB, 10,000점 약 34.5GB다. 이는 현 표본의 추정이며 더 큰 원본·다중 이미지를 포함하면 달라진다.

월비용은 DB/호스팅 기본료 + 원본·파생본·원자료 저장 + 독립 백업 + 이미지 전송 + 작업 실행 비용으로 계산한다. 전송량은 방문 수 × 방문당 이미지 수 × 실제 전달한 평균 이미지 크기로 추정하고 캐시 적중·확대 요청을 따로 측정한다. 현재 요금제·방문량을 확인하지 않아 금액을 제시하지 않는다. C03 산출물에 현재 단가, 예상 월 사용량, 월 한도, 한도 접근 시 수집 일시 중단 기준을 기록한다.

## 9. 산출물 인수와 완료 정의

**기획 완료:** 서비스 범위, 화면·자료·권한 원칙, 실제 수집 경로, 작업 의존 관계, 품질 기준, 비용 산정 방식, 공개와 복구 절차, 운영 책임을 문서로 정리한 상태다. 이번 작업은 이 범위를 완료한다.

**첫 공개 완료:** G02까지 모든 P0 산출물과 검수 증거가 존재하고 실제 운영 주소에서 핵심 흐름이 동작하는 상태다. G03은 공개 후 운영 인수 완료 기준이다. 이후 아카이빙은 지속 업무로 유지한다.

인수 시 아래 결과물을 함께 전달한다.

- 실제 환경·DB·권한표·기존 URL 이관표와 코드/데이터 버전.
- 수집 실행법·대상 조절·실패 재개·검토 대기 처리·작가 병합/분리 방법.
- 1,000점 및 공개 규모 수량·품질·성능·비용 보고.
- 콘텐츠 등록·수정·비공개 전환·이미지 중단·캐시 처리 방법.
- 백업 위치·주기·보관 정책·복원 검증 기록·배포 되돌리기 절차.
- 첫 30일 탐색·저장·원사이트 이동·작가별 깊이·운영 소요 시간과 다음 수집 목록.

작업 진행 시 표의 ID별로 상태·담당자·산출물 링크·검수 날짜를 기록한다. 선행 결과가 바뀌면 영향을 받는 후속 작업만 재검토한다. 새 기능 요청은 첫 공개 필수인지 후속인지 판단한 뒤 이 문서와 상위 기획안을 함께 갱신한다.
